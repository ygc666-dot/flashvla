## 二、克隆过慢的根因分析

### 1. 现象

首次**直连**克隆，5 分钟仅到 21%（24 MiB），平均 70–130 KiB/s，被超时中断。

### 2. 排除项（不是这些原因）

- **DNS 正常**：`github.com` 正常解析。
- **TCP 连通正常**：443 握手 `time_connect=0.07s`，`github.com` 返回 200。
- **git 元数据协商很快**：`git ls-remote` 仅 0.87s，`Enumerating/Compressing` 也是秒级完成。
- **仓库本身不大**：约 120 MB 打包数据、1017 个对象。

### 3. 真正原因

慢在**大流量数据面**，不在控制面：跨境链路 RTT 高叠加丢包，TCP 有效吞吐被压到
百 KB 级，`Receiving objects` 阶段因此龟速。`codeload.github.com` 直连更彻底失败
（15s 超时，即使用 tarball 方式备份下载也走不通）。

### 4. 实测对比

| 方式                          | 吞吐        | 结果                 |
| ----------------------------- | ----------- | -------------------- |
| 直连 `github.com`             | ~113 KB/s   | 5 分钟仅 21%，超时   |
| 直连 `codeload.github.com`    | 0（超时）   | 15s 内不可用         |
| 经本地 Clash `127.0.0.1:7890` | ~1.12 MB/s  | 1 分钟完成全量克隆   |

提速约 **10 倍**。

### 5. 本机可用的代理条件

- Clash 监听 `127.0.0.1:7890`，端口开放。
- `~/.ssh/config` 早已通过 `ProxyCommand python3 ~/.ssh/http_proxy_cmd.py` 复用同一代理
  （即 `github.com` / `github-ygc` 两个 Host 都走 Clash），只是 **HTTPS 克隆未继承该设置**。
- 当前 shell 无 `http_proxy` / `https_proxy` 环境变量，`git config --global` 也未配代理，
  所以 `git clone https://...` 始终是裸直连。

### 6. 改进方案（按推荐度）

```bash
# 方案 A：会话级注入环境变量（本次采用，不改任何全局配置，最安全）
export https_proxy=http://127.0.0.1:7890 http_proxy=http://127.0.0.1:7890

# 方案 B：只给 github 域名配代理，其余流量不受影响（会写 ~/.gitconfig）
git config --global http.https://github.com/.proxy http://127.0.0.1:7890

# 方案 C：改走 SSH 别名（已有 ProxyCommand，天然走代理）
git clone git@github-ygc:ducido/SDN.git SDN   # 需该账号有读权限
```

### 7. 排查手法备忘

```bash
# 控制面是否正常（秒级返回说明 DNS/握手没问题，问题在带宽）
time git ls-remote --heads https://github.com/ducido/SDN.git

# 数据面测速：直连 vs 代理，一眼看出差距
curl -sS -L -o /dev/null --max-time 15 -w "speed=%{speed_download}B/s\n" \
  https://codeload.github.com/ducido/SDN/tar.gz/refs/heads/main
https_proxy=http://127.0.0.1:7890 curl -sS -L -o /dev/null --max-time 15 \
  -w "speed=%{speed_download}B/s\n" https://codeload.github.com/ducido/SDN/tar.gz/refs/heads/main

# 代理端口是否在听
timeout 3 bash -c "</dev/tcp/127.0.0.1/7890" && echo OPEN
```

### 8. 若仍慢的补充手段

- `git clone --depth 1` 只取最新快照（本仓历史仅 2 条提交，收益有限，但对长历史仓库有效）。
- 克隆中断后重试前先 `rm -rf SDN`（git 会自行清理，但确认更稳妥）。
- 全局配置了无效代理导致「明明关了梯子却连不上」时，可用
  `git -c http.proxy= -c https.proxy= clone ...` 单次绕过。
