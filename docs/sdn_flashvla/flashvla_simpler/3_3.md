## 2. 转换器实现

### 2.1 与 `3_2_todo.md` §5 的对应

```143:151:sim_eval/simpler/convert_simpler_to_lerobot.py
def build_features(group: str) -> dict:
    g = GROUPS[group]
    return {
        "observation.state": {"dtype": "float32", "shape": (8,), "names": {"motors": STATE_NAMES}},
        "action": {"dtype": "float32", "shape": (7,), "names": {"motors": ACTION_NAMES}},
        IMAGE_KEY: {"dtype": "video", "shape": g["shape"], "names": ["height", "width", "rgb"]},
    }
```

- 字段映射、`STATE_NAMES`/`ACTION_NAMES`、`IMAGE_KEY = observation.images.top`、`GROUPS` 常量（fps/shape/robot_type/source_camera）与 §5.3 逐字一致；
- 截断与分流在 `plan_episode`（`153:167`）：成功 `keep = min(steps, first_success + 1 + k)`，失败 `keep = steps`；
- 三条 §5.2 硬要求：`task` **逐帧**取（`write_episode` 内 `vocab[instruction_id[t]]`）、不做 `state/action` 平移、每个写者都调 `finalize()`（`convert_task` 末尾）。

### 2.2 相对文档的四处工程改动（都是为了少踩坑，口径不变）

> **状态：已就地回写 `3_2_todo.md`**（T1 输入/验收表、T2/T3 命令、§8 路径段、§9 排期行）。
> 下表保留「改了什么、为什么」，以便对照旧版文档；`3_2_todo.md` 现在是可直接照抄的复现脚本。

| # | 改动 | 原因 | 回写位置 |
| :- | :--- | :--- | :--- |
| 1 | `--dump-root` 支持**递归发现** `seeds=*/<task>/dump/`，且可传多个根；同一 episode 经两条根被看到时**报错**（不静默双写） | P1 实际把 9 任务分散在 **4 个 `seeds=` 目录**（`1000-1149`=4 任务、`1000-1199`=2、`1000-1299`=1、`1000-1499`=2）；文档原来的单根写法会 `FileNotFoundError`（报错而非静默漏转） | T1 输入行 + T2/T3 命令 + 「实现口径」注 |
| 2 | `--group` 会自动**跳过另一机器人族的任务**（读 npz 的 `robot_type`） | 一条命令扫全目录也不会把 widowx 任务塞进 fractal 根（shape 不同会直接报错） | 同上（T2 命令不再需要 `--tasks`） |
| 3 | 写者**懒创建**，缺某个 outcome 时不生成空根 | 空 LeRobot 根会让 P3 的 `config_subdirs: [success, failure]` 自动发现失效 | T1 产出说明 |
| 4 | `--limit-per-outcome N` = 每个 (task, outcome) 最多 N 集（`--limit` 保留为别名） | 文档只写了「`--limit 2` 转 1 成 1 败」，与实现语义不符；显式命名后「1 成 1 败」只有一种写法 | T1 输入/验收行 + §9 排期行 |

另外新增 `--dry-run`（只算不写，输出 `p2_plan_dry_run.json`）、`--overwrite`（防误删，默认跳过已存在的任务根）、
以及启动时的 **safe-delete 自检告警**（见 §4 #1：钩子无法在进程内关闭，只能提示重跑时加 `CODEBUDDY_SAFE_DELETE_ENABLED=0`）。

### 2.3 实跑命令（T2 / T3）

```bash
export HF_HUB_OFFLINE=1
# 9 个任务各起一个进程；单进程 22–30 帧/s，9 进程并行 ≈45 min
python sim_eval/simpler/convert_simpler_to_lerobot.py \
  --dump-root third_party/SDN/eval_logs/p1_dump/vanilla \
  --out-root /data/zjr/simpler_lerobot/fractal --group fractal \
  --tasks <one-task> --truncate-k 2 --image-writer-threads 4
```

`--dry-run` 先对拍预测表，**一次命中**（fractal 170,091 帧、bridge 32,184 帧，逐任务全等），
所以 45 min 的编码是「已经知道结果对不对」的一次执行，而不是试错。

### 3.2 格式与窗口（G2-1/2/3）

| 检查 | 判据 | 实测 |
| :--- | :--- | :--- |
| 单样本形状 | `action [64,7]`、`action_is_pad [64]`、`state [8]`、图 `[3,H,W]` | 18 个叶子全部 PASS（fractal `[3,512,640]`、bridge `[3,480,640]`） |
| pad 结构 | 第 k 块前 `k·C` 行继承基础样本，其余恒 True | 逐块 `torch.equal` 全等（`check_samples`） |
| 窗口不跨 episode | 第 idx 帧的真实行数 == `min(to_idx − idx, N·C)` | **3,918 个边界样本**（首/中/末帧 × 全体 episode）无一例外 |

> 实现细节：`action_is_pad` 已经是「按 config 块」的版本，基础样本要以**第 N 块**反推
> （`k·C == H_cfg`，该块既不补零也不补 pad）。文档里的 `[16,7]` 单块长度容易让验收写错，
> 这里按 §6 的警告统一成 `[64,7]`。

### 3.3 统计量（G2-4）——相对误差 1e-9 量级［已核实］

| 训练集 | 帧数 | action `|mean|max` / `|std−1|max` | state 同 |
| :--- | ---: | :--- | :--- |
| fractal `[success]` | 50,843 | 4.0e-09 / 5.2e-08 | 1.0e-07 / 5.9e-07 |
| fractal `[success,failure]` | 170,091 | 4.7e-09 / 6.4e-08 | 2.6e-08 / 2.9e-07 |
| bridge `[success]` | 17,784 | 4.1e-09 / 7.1e-09 | 4.4e-08 / 8.4e-07 |
| bridge `[success,failure]` | 32,184 | 2.6e-09 / 8.0e-09 | 2.4e-08 / 3.4e-07 |

判据是 1e-3，实测优于它 5 个数量级：LeRobot 的 `aggregate_stats` 是**按 count 加权**的
（`compute_stats.py:570-607`），所以「叶子统计量池化」严格等于「全体帧的全局统计量」，
按根混装也不会让 `MEAN_STD` 失真 —— §9 风险 8（失败帧长尾）由此被自动吸收。

## 4. 踩到的坑（都已修，值得记下来）

| # | 现象 | 根因 | 处理 |
| :- | :--- | :--- | :--- |
| 1 | 首次 9 个转换进程在第 1 集 `save_episode` 全部崩溃：`[safe-delete] trash operation: /data/.Trash-1000 Permission denied` | IDE 的 `sitecustomize.py` 钩子把 Python 的删除动作改成「移入回收站」，`/data` 下无回收站目录 | 起进程时加 `CODEBUDDY_SAFE_DELETE_ENABLED=0`（仅影响本 IDE 终端里的进程；普通终端无此钩子） |
| 2 | `LeRobotDataset.create(root=...)` 在已存在的空目录上报 `FileExistsError` | v3 的 `create` 要求 root **不存在** | `ensure_writer` 先删空目录再 create；非空时明确要求 `--overwrite` |
| 3 | `np.stack(list(imageio.get_reader(mp4)))` 抛 `MemoryError` | LeRobot 写的 mp4 `nframes=inf`，`Reader.__len__` 返回 `2**63-1`，`list()` 按此预分配 | 一律用 `[f for f in reader]` 或 `reader.get_data(i)` 切片 |
| 4 | 转换期间用真实 config 建数据集，报 `Parquet magic bytes not found` | 任务根在转换中已存在 `meta/info.json`，被自动发现，但 parquet 还没写完 | 属预期：P3 只在全部转换完成后读。T4 也因此放在全部任务结束后跑 |
| 5 | 文档里 `--dump-root .../seeds=1000-1499` 只含 2 个任务 | P1 的 9 个任务分散在 4 个 `seeds=` 目录 | 转换器改为递归发现（§2.2 #1） |

另外两个「差点写错」的验收口径（不是坑，但会误判）：

- `action_is_pad` 的**基础样本**必须从第 N 块反推，否则会以为「pad 应该全 True」；
- `observation.state` **不要**放进 `delta_timestamps`（`PI05Config.observation_delta_indices` 是 `None`），
  否则状态会变成 `[1,8]` 而不是 `[8]`。

### 4.1 首轮崩溃的残留核查（2026-11-21 事后清点）［已核实］

首轮（未加 `CODEBUDDY_SAFE_DELETE_ENABLED=0`）9 个进程都在第 1 集收尾时崩，随后整组删盘重跑。
逐项核查结论：**没有未解决的数据残留**。

| 检查 | 结果 |
| :--- | :--- |
| 18 个根的内部一致性 | 逐根核对 `len(meta/episodes) == total_episodes`、`sum(episodes.length) == total_frames == parquet 实际行数`：**18/18 全等** |
| 半成品文件 | 根内无 `*.png` / `*.tmp` / `*.lock`；`images/` 只剩**空目录树**（lerobot 只 unlink 文件、不 rmdir，属上游行为，无体积） |
| 孤儿进程 | `pgrep convert_simpler` = 0 |
| `/data` 下的回收站 | 不存在（创建失败正是首轮崩因），无垃圾目录 |
| 家目录回收站 | `~/.local/share/Trash` 共 70 GB，但只有 **2 个空目录条目**（`fractal`/`bridge`，各 <4 KB）源自本次；其余 70 GB 为 11-16/17 的旧实验（`train_none_merged` 15 G、`train_l3_merged` 15 G 等），与 P2 无关 |
| 首轮产出的 ~0.3 GB | 已在重跑前整组 `rm -rf` 真实删除，未进回收站、未混入最终数据 |

唯一可选的清理项：18 个根里各有一套空的 `images/observation.images.top/chunk-000/` 目录
（共 18 × 2 层空目录）。不占空间，删不删都不影响 P3 读取。
