## 1. 数据契约（先定，P2 依赖它）

### 1.1 落盘结构

```
third_party/SDN/eval_logs/p1_dump/
└── vanilla/seeds=1000-1499/<task>/          # 沿用 evaluate.py 原有的 result_dir 命名
    ├── 000_episodes.json                    # 逐 seed 成败（evaluate.py 原生）
    ├── 000_episode_stats.json               # steps / first_success / qpos / speed
    ├── 000_success_<rate>.log               # 汇总日志（任务跑完才改名）
    └── dump/
        ├── episode_01000.npz                # 44 KB（200 步）
        └── episode_01000.mp4                # 3.9 MB（200 帧，h264）
```

同一 `dump/` 里**成功与失败轨迹混放**（方案 §3.2 明确要求，失败轨迹留给 P3 的抗漂移增广），
靠 npz 的 `meta.success` 区分。

### 1.2 npz 字段

| 键 | 形状 | dtype | 含义 |
| :--- | :--- | :--- | :--- |
| `proprio` | `[T, 8]` | f32 | `obs['agent']['eef_pos']`，**反归一化前的 raw 值** |
| `action` | `[T, 7]` | **f64** | 交给 `env.step` 的 7 维向量，**逐位相同** |
| `world_vector` / `rot_axangle` / `gripper` | `[T,3] [T,3] [T,1]` | f64 | 上者的三个分量，用于离线复核（`concat == action`） |
| `reward` / `success` / `truncated` | `[T]` | f32 / bool / bool | 每步 env 返回 |
| `query_index` | `[T]` | i32 | 该步动作由第几次 policy 查询产生 |
| `query_step` / `query_instruction_id` | `[Q]` | i32 | 每次查询发生在第几个 env step / 用的哪条指令 |
| `raw_chunk` | `[Q, 4, 7]` | f32 | 该次查询的**原始输出（反归一化前）** |
| `instruction_id` / `instruction_vocab` | `[T]` / `[V]` | i32 / U192 | 逐帧指令（去重存词表） |
| `meta` | 标量 | json | task / episode / robot_type / camera / fps / steps / first_success … |

### 1.3 三条与 P2 约定的口径

1. **一行 = 一次 `env.step`**（google 3 Hz、widowx 5 Hz）。`obs` 行 t 是动作用于的观测，
   `action` 行 t 是真正执行的动作 —— 因此第 1–3 行是**开环执行**的 chunk 行，不是「新观测算出来的动作」。
   两种视图都能从 `query_index` / `query_step` / `raw_chunk` 重建。
2. **`first_success` 是 0-based 索引**，与 `eval_utils.stat_first` 同口径；
   保留帧数 = `first_success + 1 + k`。
3. **图像只存单相机原分辨率**（google `overhead_camera` 512×640、widowx `3rd_view_camera` 480×640），
   不提前 resize。h264 有损（14.4 KB/帧），选它是因为 P2 的 LeRobot `use_videos=True` 本来就要再编一次；
   需要无损时 `--dump-images npz` 改存进 npz（体积 ×10）。

## 2. 三处代码改动（对应方案 §3.1）

### ① dump 钩子（方案 §3.1①）

```217:290:third_party/SDN/policy/pizero/evaluate.py
        dumper = self._build_dumper(episode) if self.dump_episodes else None
        ...
            if dumper is not None:
                dumper.begin_query(raw_chunk, instruction, timestep)
            for action in actions:
                obs_image, obs_proprio = image, obs['agent']['eef_pos']
                command = np.concatenate([...])
                obs, reward, success, truncated, info = env.step(command)
                ...
                if dumper is not None:
                    dumper.add_step(image=obs_image, proprio=obs_proprio, command=command, ...)
        ...
        if dumper is not None:
            dumped = dumper.finalize(first_success=info.get('first_success', -1))
```

三处刻意设计：

- **接住 raw chunk**：`policy.step` 的第一个返回值原来被 `_` 扔掉，现在喂给 `begin_query`，
  同时可用于复核归一化/反归一化没有错位（方案 §3.1 的警告点）；
- **把 `proprio` 读进内层循环**：只读在 chunk 起点的话，第 1–3 行会拿到陈旧 proprio；
- **`obs_image` 取 `env.step` 之前的那一帧**：内层循环里 `image` 在 step 之后才更新，
  取早了会整体错位一帧（这类错位不会报错，只会让 BC 学到「慢半拍」）。

### ② `--start-seed`（方案 §3.1②）

```426:428:third_party/SDN/policy/pizero/evaluate.py
    parser.add_argument("--start-seed", type=int, default=0,
                        help="first episode seed; keep the collection seeds disjoint from the eval seeds")
```

`ParallelRunner.__init__` 里 `list(range(n_trajs))` → `list(range(start_seed, start_seed + n_trajs))`。
`result_dir` 命名逻辑无需改（原有代码已经把非 `0-49` 的 seed 段写进目录名）。

### ③ 一条断言（方案 §3.1③）

```153:163:third_party/SDN/policy/pizero/dump_utils.py
        if self.verify:
            rebuilt = np.concatenate([
                _to_numpy_1d(world_vector),
                _to_numpy_1d(rot_axangle),
                _to_numpy_1d(gripper),
            ]).astype(np.float64)
            if not np.array_equal(rebuilt, command):
                raise AssertionError(...)
```

外加两条同类断言：`finalize` 时把 dumper 自己算的 `first_success` 与 `evaluate.py` 的
`info['first_success']` 对拍（不一致即抛），以及 `check_raw` 离线再核 `concat == action`。

> 这条断言不是形式主义：它在上线第一天就抓到一个真 bug（§3 坑 1）。

### ④ 方案外的三处加固

| 改动 | 为什么 | 位置 |
| :--- | :--- | :--- |
| `--dump-images {mp4,npz,none}` | 空间/无损/冒烟三档；`none` 用于纯数值冒烟，10 s 级验证链路 | `evaluate.py:434-436` |
| `_dump_complete()` | 原逻辑「已完成就跳过、未完成就 rmtree 重来」在采数下是灾难（中断一次丢 500 集）；改成「dump 不完整才重来」 | `evaluate.py:372-376` |
| `if ! python ...; then FAILED+=()` | `set -e` + for 循环会让某任务的崩溃杀掉后面 10 小时；改成记录失败继续跑，末尾统一报 | `run_episode_dump.sh:77-91` |

## 3. 五个坑

| # | 现象 | 原因 | 解法 |
| :- | :--- | :--- | :--- |
| 1 | 第一个 step 就 `AssertionError`：`0.051197424...` vs `0.051197424...` 末位不同 | 我把三个动作分量先 `.astype(np.float32)` 再重建，而真实命令是三个 **float64** 分量的 `np.concatenate`（`denormalize_bound` 返回 f64；`gripper` 由 Python float 转来也是 f64） | `_to_numpy_1d` 默认保持 f64，只有 `raw_chunk` 显式转 f32（`dump_utils.py:58-68`） |
| 2 | 潜在：80 帧可能全是同一张（渲染缓冲被复用） | `obs['image'][cam]['rgb']` / `eef_pos` 可能是复用缓冲的视图 | 存前 `np.array(..., copy=True)`；实测本版 sapien 不复用（80 帧 `tobytes` 两两不同、帧间差分非零） |
| 3 | `RuntimeError: Program 'ffmpeg' is not found` | 系统 PATH 无 ffmpeg（`evaluate.py` 的 gif 分支靠 `module load` 才能跑） | dump 走 `imageio` + `imageio_ffmpeg` 自带二进制，不依赖 PATH；采数脚本一律 `--no-video` |
| 4 | 中断一次就要重采整个任务 | `_set_result_dir` 的 rmtree 语义 | `_dump_complete()` 判定，见 §2④ |
| 5 | 若沿用 R1 的 `reload_every=8`，2300 集要多花 ~5 h | 每次重建 = 环境 init + ckpt load + `torch.compile` ≈ 50 s（实测 63.9 s 冷启动，其中推理只占 16 s） | 默认改 50；实测 20 集连跑显存恒定 8.1 GB（`gc.collect()+empty_cache()` 每集都跑） |

坑 1 的教训值得单独记一句：方案 §3.1③ 说「这是整条管线最容易静默错位的地方」，
实测确实错在这里，而**错的方式连肉眼比对都看不出来**（0.05119742453098297 vs 0.051197424888086956），
只有 `np.array_equal` 能抓。

### 4.3 一个必须先说清的种子问题

本批数据的 vanilla π0\* 宏平均 = **67.2%**（seeds 1000-1499），而

| 对照 | 宏平均 | seeds |
| :--- | ---: | :--- |
| 论文 π0\*（Table II） | 63.9% | 未公开 |
| R1 的 **π0\*+SDN**（`results.md` §2） | 67.3% | 0-49 |
| **本批 vanilla π0\***（P1 采数集，即 teacher 的训练数据成功率） | **67.2%** | 1000-1499 |

三行数字摆在一起，两种解释都能成立：**(a) seeds 1000-1499 比 0-49 好做**；
**(b) SDN 的增益被种子噪声吃掉**。本文不能区分［待核实］，但两条结论已经确定：

1. **G3 的基线只能在留出 seeds 上重新测**，拿 R1 的 67.3%（seeds 0-49）去比是跨种子比较，不可用；
2. 若想确认是 (a) 还是 (b)，最小代价是补跑 **vanilla 在 seeds 0-49**（9 任务 × 50 集 ≈ 3.5 h），
   与本表同口径对照 —— 顺带补齐 `results.md` §9 一直缺的「π0\* 本机 vanilla 臂」。

- `google_robot`（`EDRSimplerAdapter`，fractal 配置）：**连续值**，实测落在 `[-1.15, +1.15]`

- `widowx`（`BridgeSimplerAdapter`）：**严格二值** `{−1, +1}`（`2·(a>0.5)−1`）。

`proprio` 8 维（`eef_pos` = xyz + wxyz 四元数 + 开合度），实测各维 std 在 0.05–0.35，
无常数维、无越界（google 第 8 维 p99 = 1.0）［已核实］。

| 帧数 | ≈4 万 | **26.3 万（截断后 6.9 万）** | 方案只数了成功轨迹的截断帧；落盘全量 |
| 图像存储 | 「mp4 另存可省 10× 空间」 | mp4 (h264, 14.4 KB/帧) 为默认，npz 可切 | 一致 |
| G1 的 `first_success` 阈值 | 中位数 < horizon×0.6 | apple 165 > 120 | 见 §5.2 |

### 5.2 `apple` 的 `first_success` 越界：判为已知风险，不阻断

`place_apple_in_closed_top_drawer` 的 horizon 是 200，π0\* 的成功轨迹中位首达步是 **165**（83% of horizon），
超过方案定的 0.6 阈值。含义与处置：

- **不是采数 bug**：该任务论文 π0\* 只有 17%，本批 23.4%（117/500），成功率正常；失败集全部 `first_success = −1`
  （无「做成了又丢掉」的情况，与 `results.md` §5 的观察一致）。
- **真实含义**：π0\* 在 apple 上就是「慢慢磨到第 165 步才成」，方案 §3.3 的阈值本意是「策略在磨 → 训练学会磨」。
- **对 P1 不阻断**：数据本身合格（117 条成功、20,273 可训练帧），且 `k` 的取值由 P2 决定；
  k=0/2 时每条成功轨迹仍有 ~165 帧，够 P3 用。
- **对 P3 是风险信号**：G3 的「不磨」判据（成功 `first_success` 均值不超过 π0\* 的 1.5×）在 apple 上
  会非常宽松（上界 255 > horizon 200，等价失效）。建议 apple 单独看「是否在 200 步内成功」，
  而不是看首达步。这与方案 §8 风险 2（单相机导致 apple / stack_cube / carrot 崩）是同一条线上的。

### 5.3 墙钟 17.6 h 而不是 12 h

差异全部来自 GPU4 被共享（另一个作业常驻 18.6 GB、util 100%），不是实现问题：
- 同一任务 `coke_can`：冒烟阶段 0.196 s/step → 正式采数 0.227 s/step（+16%）；
- 长 horizon 任务（apple 200 步、open_drawer 116 步）占全量帧的 60%，对 pace 更敏感；
- 9 次冷启动（每次 64 s）合计仅 10 min，不是主因。

若要压缩：把 apple 500→300、open_drawer 500→350（成功条数 117→70、223→156），
其余 7 个任务不变，合计 **≈13.4 h**（原 17.6 h 中这两个任务占 11.6 h），仍满足 G1 的 ≥50 条。
**不建议重采**：当前数据已经够用，且质量与确定性都已验证。

## 6. 对 P2 / P3 的交接

### 6.1 P2 必做的三件事（方案 §4 不变，但多两条输入）

1. **两个顶层数据集**：`fractal`(3 Hz) 与 `bridge`(5 Hz) 分开建 —— `MultiFlashVLADataset` 会因 fps 不一致
   直接 `raise`（`flashvla/datasets/flashvla_dataset.py:150-151`）。本批帧数 google 209,200 / widowx 54,000。
2. **stats 必须重算**，用 §4.4 的表对拍（相对误差 <1e-3 是 G2 的判据）。
3. **截断口径**：`first_success` 0-based，保留 `first_success + 1 + k` 帧；k=2 时全量 68,627 帧。

### 6.2 两条新增输入

- **指令不是退化的**：`move_near` 有 **26 条**不同指令（随场景物体变），`close_drawer`/`open_drawer` 各 3 条，
  其余 1–2 条。P2 转 LeRobot 时把 `instruction_vocab[instruction_id]` 逐帧展开成 `task` 字段即可，
  不需要额外标注。
- **失败轨迹 994 条已在同一目录**（`meta.success = false`），P3 §5.3 的「混 10–20% 失败/未截断轨迹」
  不需要重采，只需在 P2 的转换器里加一个 `--include-failures` 开关。

### 6.3 P3 的 `steps`：一个 epoch = 总帧数，不是总帧数/16

一个样本的上下文是 `N·C = 16` 帧动作（§4.3 的 `action.shape == [16, 7]`），但**样本数不等于帧数/16**：

- `PI05FlashVLAConfig.action_delta_indices = list(range(total_action_horizon))`
  （`flashvla/policies/pi05/configuration_pi05.py:248-249`），`observation_delta_indices = None`（单帧图像+状态）；
- `LeRobotDataset.__len__` 直接返回 `num_frames`（lerobot 0.5.1），episode 尾部靠 pad 补齐
  —— 这正是方案 §4.3 那条「最后 N·C 帧被正确 pad」的检查要覆盖的行为。

所以 **一个 epoch 的样本数 ≈ 总帧数**：

```
68,627 帧 → ≈ 68,627 样本/epoch → batch 32 下 ≈ 2,144 step/epoch
steps 12000 ≈ 5.6 epoch ≈ 38 万样本（LIBERO 配方 50k×32=160 万的 24%）
```

结论：方案 §5.1 的 `steps: 12000` **量级是对的，不需要重算**。
（本文初稿曾按「帧数 ÷ 16」估成 90 epoch，核对 `__len__` 与 `action_delta_indices` 后已纠正。）
若要更靠近 LIBERO 配方，可到 25k–50k step，但要配 G3 的离线 L1 早停 —— 6.9 万帧撑 20 epoch
以上仍有明显过拟合风险。［待核实：P2 落完后 `len(dataset)` 一测即得准确 epoch 长度。］

### 6.4 G3 的基线还缺一个数：π0\* 在留出 seeds 上的成功率

方案 §5.4 的判据是「M=1 在留出 seeds 上 macro ≥ π0\* − 2 pp」。现在的情况：

| 需要的数 | 现状 |
| :--- | :--- |
| 学生（FlashVLA M=1）在留出 seeds 的 macro | P3 才产出 |
| **π0\* 在留出 seeds 的 macro** | **缺** |

因为采数占用了 1000-1499，留出集必须另起（建议 **2000-2049**），并在这批 seeds 上补测 π0\* vanilla。
成本 ≈ 9 任务 × 50 集 = 44,600 env step ≈ **3 h**（按 0.24 s/step 加 9 次冷启动）。命令：

```bash
cd third_party/SDN
for t in <9 tasks>; do
  python -m policy.pizero.evaluate --method vanilla --task "$t" \
      --n-trajs 50 --start-seed 2000 --result-root ./eval_logs/p3_baseline --no-video
done
```

**这条不做，G3 无法判定**（拿 seeds 0-49 的 67.3% 去比会引入 §4.3 那 3 pp 量级的种子偏差，
而门槛只有 2 pp）。
