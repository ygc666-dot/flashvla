**一句话结论**：成功率的复现质量很好（两模型偏差都在 ±1.3 pt 内，且相对排序与论文一致）；**唯一的显著偏差集中在单步耗时**，且不对称——**π0.5 侧对得上，FlashVLA 侧对不上**。

**根因（详见 §5）**：本机每步有约 **35 ms 的"非模型地板"**（MuJoCo 物理 + EGL 双视角渲染 + 观测预处理），占 π0.5 单步时间的 **72%**。FlashVLA 只能消掉其中的"推理份额"（≈14 ms → ≈4 ms），因此理论上限就是 **1.39×**，实测 1.28× 已达上限的 92%。而论文的 22.1 ms 意味着他们的地板必须 **≤ 22 ms**（约为本机的一半），两者不在同一个可比区间内。

## 4. 单步耗时拆解（核心分析）

### 4.1 拆解方法

评测实现里每一步的动作来源分两类，日志中分别统计（`sim_eval/libero/eval.py:258-263`）：

- `transition`：取到新的 action chunk 的那一步（含阻塞等待推理完成的全部时间）
- `internal`：复用缓存 chunk 的普通步（实测 ≈ 0.01 ms，可忽略）

于是可以把单步耗时分解为：

```
Time/Step  =  摊销推理成本  +  非模型地板
                ↑               ↑
   (transition 均值 × 每次 episode 的 transition 次数 / 步数)
                                MuJoCo/robosuite 物理 + EGL 渲染 2×360×360
                                + resize 到 224 + 归一化 + 动作反归一化/限幅 + 线程同步
```

这个拆解可以**交叉验证**：地板是模型无关的，所以两个模型在同一套件上算出的地板应当相等。下表正是如此。

### 4.2 拆解结果（5 seed 平均，ms/step）

| Suite | π0.5 单步 | π0.5 摊销推理 | **π0.5 地板** | FV 单步 | FV 可见等待 | **FV 地板** | 地板一致性 |
| :-- | :--: | :--: | :--: | :--: | :--: | :--: | :--: |
| Spatial | 64.83 | 14.86 | 49.98 | 46.85 | 2.67 | 44.18 | Δ5.8（负载差异） |
| Object | 45.85 | 13.93 | 31.92 | 36.92 | 4.50 | 32.42 | **Δ0.5** |
| Goal | 47.96 | 13.53 | 34.43 | 38.83 | 4.19 | 34.64 | **Δ0.2** |
| Long | 41.51 | 13.56 | 27.95 | 34.01 | 4.43 | 29.58 | Δ1.6 |
| **平均** | **50.04** | **13.97** | **36.07** | **39.15** | **3.95** | **35.20** | **Δ0.9（2.4%）** |

**这张表把整个故事讲完了：**

1. **地板在两条评测中几乎完全一致**（36.07 vs 35.20 ms，差 2.4%）。这既验证了拆解方法，也说明**两轮评测的仿真/渲染环境是同一个、可比的**。
2. **FlashVLA 的全部收益都来自推理**：13.97 → 3.95 ms/step（−10.02 ms），单步降幅 −10.89 ms 中 **92% 由推理贡献**。
3. **地板占 π0.5 单步的 72%**。也就是说，即使把推理成本压到 **0**，单步也只能从 50.04 降到 36.07，即 **1.39× 封顶**（实测 1.28×，已达上限的 92%）。
4. **FlashVLA 的可见等待只有 2.7–4.5 ms/step**，`transition/internal` 比值 540–680×，日志里 `overlap_steps=1` 的异步管线**确实把推理藏住了**——方法本身在小尺度上是成功的，问题在分母。

### 4.3 与论文的结构性对比

由 `加速比 = (S + I_base) / (S + I_fv)` 反解"地板占比"：

| | π0.5 单步 | FlashVLA 单步 | 加速比 | 反解：推理占地板外单步的比例 |
| :-- | :--: | :--: | :--: | :--: |
| **论文** | 53.8 | 22.1 | 2.43× | 推理 ≈ **59%**，地板 ≈ 41% |
| **本机** | 50.04 | 39.15 | 1.28× | 推理 ≈ **28%**，地板 ≈ 72% |

两边 π0.5 的单步总量只差 7%（53.8 vs 50.04），但**内部构成完全相反**：

- 论文环境：**"推理密集型"** —— 推理是主要成本，加速推理就能拿到 2.4×；
- 本机环境：**"仿真密集型"** —— 仿真/渲染是主要成本，加速推理最多只能拿到 1.4×。

**这就是全部差异的第一性原因，不是实现问题。**

## 5. 与论文差异的原因分析

### 5.1 成功率：属于"复现噪声"，不是方法问题

| 观察 | 量级 | 判断 |
| :-- | :-- | :-- |
| π0.5 在 Goal 上偏低 2.84 pt | 单套件 | 最可疑。基线权重是 lerobot 格式的 `pepijn223/pi05_libero_31_9_non_q`，**不是** openpi 的 JAX 原始权重，Goal 恰好是对权重/初始化最敏感的套件 |
| 两模型在 Spatial 上都偏低 1.7–2.2 pt | 跨模型一致 | 系统性环境偏差（机器/渲染/初始状态读取），与策略无关 |
| Object / Long 基本逐格吻合（−0.3 / −0.1） | ≤0.4 pt | 说明管线、归一化、episode 上限（280/280/300/520）都是对的 |
| ΔSR 方向一致（+1.50 vs 论文 +0.9） | 0.6 pt | 结论稳健 |

**判断**：SR 侧可以认为**复现成功**，残差 0.7–1.3 pt 可由"检查点来源 + 单一评测环境"解释，不构成对方法的挑战。

### 5.2 单步耗时：分歧只在 FlashVLA 一侧

| 对象 | 论文 | 本机 | 偏差 |
| :-- | :--: | :--: | :--: |
| π0.5 单步 | 53.8 ms | 50.04 ms | **−7.0%（对得上）** |
| FlashVLA 单步 | 22.1 ms | 39.15 ms | **+77.1%（对不上）** |

这个**不对称**本身就是最强的线索：如果只是"我们机器慢"，两边应该等比变慢；实际是基线对得上、加速后的那一侧对不上。用 §4.2 的拆解直接读出矛盾：

> **论文的 22.1 ms 低于本机实测的"零推理地板"（35.2 ms，Spatial 甚至 44 ms）。**
> 也就是说，在本机的仿真/渲染配置下，**一个完全不花时间的策略也跑不到 22.1 ms/step**。

因此差异不可能只由"模型更快/更慢"造成，必然来自**分母（每步固定开销）的差异**。

### 5.3 假设清单（按可能性排序）

#### H1（最可能，权重 ≈ 50%）—— 两轮的"每步固定开销"根本不同

- **证据**：地板 35.20 ms（本机）vs 论文必须 ≤ 22.1 ms（由 22.1 − 推理摊销反推）。本机地板高出 **≥60%**。
- **可导致本机地板偏高的具体项**（都可单独验证）：
  1. **CPU 线程税**：本机 112 核，`eval.sh` 默认 `OMP_NUM_THREADS=16`。脚本自己的注释就写明"在 48 线程机器上实测 +8 ms/step 的 OpenMP 同步税"。112 核下 16 线程仍可能过订阅，观测预处理（resize/归一化等小张量算子）每一步都在付这笔税。
  2. **共享节点争抢**：8×L40S / 112 核被多人共用，`batch_size=1` 时单进程几乎无法占满资源，CPU 调度抖动直接进地板。日志已给出铁证——Spatial 的 π0.5 地板在 seed1000 约 **64.8 ms**、在 seed5000 约 **46.0 ms**（同一份配置、同一个脚本）。
  3. **渲染路径**：EGL 离屏渲染 2 路 360×360（`observation_height/width=360`）再 CPU resize 到 224。若论文侧用了更低的渲染分辨率、单视角、或把 resize 放到 GPU，地板可差 10–20 ms。日志里还有 `No OpenGL_accelerate module loaded` 警告，说明部分 GL 加速模块未启用。
  4. **串行评测**：`max_parallel_tasks=1`、`batch_size=1`，每步只处理一张观测，GPU 利用率长期 <5%（当前 `nvidia-smi` 为 0–3%），纯延迟受限，无吞吐摊薄。

- **反驳/限制**：如果只是"本机整体慢"，π0.5 的 53.8 也应该对不上，但它对上了（−7%）。所以 H1 单独不足以解释全部，需要与 H2 联合。

#### H2（很可能，权重 ≈ 30%）—— 论文两组耗时数字并非同一窗口/同一口径测得

用"地板恒定"这个约束做自洽性检验：

- 论文 π0.5：53.8 = S + I_base；论文 FV：22.1 = S + I_fv。得 `S ≤ 22.1`。
- 但论文自己的推理延迟表说：π0.5 单次调用 **55.4 ms（4090，3 视角）**、FlashVLA **26.7 ms（2 视角）**。以每 5 步重规划计，摊销后分别只有 **11.1 / 5.3 ms/step**。
  > 数据出处：`README.md:106-110` 的 "Latency Benchmark" 表（`benchmarks/benchmark_latency.py` 测得，100 次采样、10 次 warmup、开启与本评测相同的 CUDA Graph + kernel fusion）。原表 π0.5 = 45.8(4090,2v) / **55.4(4090,3v)** / 37.0(5090,2v) / 44.8(5090,3v)；FlashVLA = **26.7(4090,2v)** / 36.8(4090,3v) / 20.3(5090,2v) / 27.1(5090,3v)。
  > 这里取 55.4 与 26.7 是**刻意匹配本评测的真实输入配置**：本机 π0.5 基线 `empty_cameras: 1` → 共 3 路图像槽位，FlashVLA `empty_cameras: 0` → 2 路。若换成同视角数的成对口径（2v: 45.8 vs 26.7；3v: 55.4 vs 36.8），下面的自洽性矛盾仍然成立，结论不变。
- 若 S ≈ 18 ms，则 π0.5 应为 29 ms、FV 应为 23 ms —— **π0.5 的 53.8 对不上**（差 1.85×）。
- 若 S ≈ 42.7 ms（由 π0.5 的 53.8 − 11.1 反推），则 FV 应为 48 ms —— **FV 的 22.1 对不上**（差 2.2×）。

> **结论：论文这两格数字无法用"同一个仿真地板"自洽解释，至少有一格是在不同条件下测的。**
> 本机数据恰好证明这种失真有多大：同一份 π0.5 配置，仅因外部负载不同，单步就在 **56.9 ↔ 86.1 ms** 之间摆动（1.51×）。**这正是"两轮不在同一窗口"的典型症状**——FV 侧时间窗为 10-30 → 11-05，π0.5 侧为 11-02 → 11-13，两轮覆盖的负载环境不同；更直接的证据是 π0.5 内部本身就有并发重叠：seed4000 与 seed5000 的 spatial 任务分别在 11-13 10:35 与 10:43 启动（同一时段两个进程争抢），前者单步 63.29 ms vs 后者 56.92 ms。

#### H3（次要，权重 ≈ 15%）—— 异步管线在小 chunk 下有摊销不足

- 本机 FlashVLA 的 `chunk_size=10` / `n_action_steps=5`，日志显示**每 episode 触发 46.8–107.3 次 `transition`**（Spatial 平均每 2.6 步一次、Long 每 2.5 步一次），远高于 π0.5 的每 5 步一次。
- 每次 transition 都要做一次线程 rendezvous（实测 p95 = 15–24 ms，max 76–92 ms），这些 p95/max 尾巴会直接抬高地板的方差与均值。
- 如果论文侧用更大的 chunk 或更懒的刷新策略，transition 次数更少，尾巴更短。

#### H4（次要，权重 ≈ 5%）—— 观测后处理仍是串行瓶颈

- `transition` 只统计了"等 chunk"的时间，**不包含主线程上的观测组装**（2×360×360 → float → resize 224 → normalize → stack → H2D）。这部分在异步设计里**没有被隐藏**，是地板的一部分。若论文侧把这段部分放到后台线程/GPU，地板会下降。

### 5.4 为什么本机加速比"上不去"——可操作清单

| 杠杆 | 预期效果 | 风险 |
| :-- | :-- | :-- |
| 下调 `OMP_THREADS`（16 → 4/8）或 `taskset` 绑核 | 地板 −5~10 ms，加速比 1.28× → 1.35×+ | 极低，脚本已支持 `OMP_THREADS=` |
| 低负载窗口独占 GPU/CPU，两模型**交替**重测（同一 session 内 A/B/A/B） | 消除 H2 的窗口偏差，比值可信 | 极低，只需重跑 |
| `batch_size` / `max_parallel_tasks` > 1（多 task 并行） | 提高 GPU 利用率，摊薄地板 | 改变"单流"时延语义，需同时报告单流数字 |
| 降低渲染分辨率或把 resize 挪到 GPU | 地板 −5~15 ms | 可能影响 SR（观测分布变了） |
| 用 `benchmarks/benchmark_latency.py` 单独测纯推理延迟 | 得到与地板解耦的"模型侧"数字，可直接对标论文 45.8/26.7 ms 表 | 无风险，建议必做 |

## 6. 局限与不确定性

1. **两轮评测不同窗口**（π0.5 侧 11-02→11-13、FV 侧 10-30→11-05，且 π0.5 内部有并发重叠），这是最大的不确定性来源，直接导致 §3.2 的 1.3–1.5× 抖动。
2. **地板包含 `env.reset`**：每 episode 的 reset（读初始状态 + 场景 settle）计入墙钟，短 episode（Spatial ~108 步）受影响更大，粗略估计贡献 1–3 ms/step。
3. **Spatial 地板显著高于其他套件**（44–50 ms vs 28–34 ms），两模型一致，属套件属性（接触更密集/物体更多）+ 负载叠加，尚无定论。
4. **检查点来源不同**：基线是 lerobot 格式移植权重，非 openpi JAX 原始权重，π0.5 在 Goal 上的 −2.84 pt 有相当一部分应归因于此。
5. **`transition` 不是纯推理延迟**：它是"主线程等 chunk 的时间"，FlashVLA 的真实推理耗时藏在后台线程里（本机不可直接观测）。论文对比时应区分"单步耗时 / transition / 纯推理延迟"三类指标（README 已明确警告这一点）。
6. **论文自洽性存疑**（§5.3 H2）：`Time/Step` 的构成无法用单一地板模型同时解释 53.8 与 22.1。建议核对原始测量脚本与运行日志，而不是只对比汇总表。

## 7. 结论

1. **方法有效，且复现成立**：本机 5 seed × 10 000 episode 显示 FlashVLA(d=1) 相对 π0.5 **+1.50 pt**（McNemar p < 1e-6），收益集中在 **Long +3.48** 与 **Object +1.64**，与论文（+0.9，Long +3.0）方向一致、幅度更大。成功率绝对水平低 0.7–1.3 pt，属检查点来源与单环境评测的残差。
2. **效率侧的结论必须带着"地板占比"一起说**：本机实测 **1.28×**（单步）/ **1.21×**（墙钟），论文 **2.43×**。差距**不是实现缺陷**——本机每步有 **35.2 ms 的非模型固定开销**，占 π0.5 单步的 **72%**，这个结构决定了理论上限只有 **1.39×**，实测 1.28× 已达上限的 92%。
3. **FlashVLA 的推理优化本身是有效的**：摊销推理 **13.97 → 3.95 ms/step（−72%）**，可见等待仅 2.7–4.5 ms，异步重叠把推理基本藏进了仿真窗口。
4. **论文的 22.1 ms 与本机地板不自洽**：22.1 < 35.2（本机零推理地板），且与论文自身的推理延迟表（55.4 / 26.7 ms）无法同时成立。**最可能是两格耗时在不同条件下测得**，本机的 1.51× 窗口内漂移就是同类失真的实证。
5. **与审稿人/读者沟通时的正确说法**：不是"我们复现不出 2.43×"，而是"**在本机（共享 8×L40S、112 核、EGL 双视角 360×360）的仿真地板下，端到端加速比的物理上限是 1.39×，我们到了 1.28×；论文 2.43× 对应的是一套地板 ≤22 ms 的测量环境**"。

## 8. 建议的下一步实验（按性价比排序）

1. **单流 A/B 交替重测**（必做）：同一 session、同一张空闲卡，`π0.5 → FV → π0.5 → FV` 各跑 1 个 seed，彻底消除窗口偏差，得到可信的比值。
2. **纯推理延迟对标**（必做）：`python benchmarks/benchmark_latency.py --config_path=benchmarks/configs/latency_flashvla.yaml --num_views=2/3`，把"模型侧"数字与论文 45.8 / 26.7 ms 直接对齐，与地板解耦。
3. **地板最小化实验**（推荐）：`OMP_THREADS=4` + `taskset` 绑核 + 独占 GPU，重测 π0.5 与 FV 各 1 个 seed，验证地板能否从 35 ms 压到 25 ms 以下；若能，加速比会显著上升，可直接支撑"地板假说"。
4. **`d=0` 消融**（推荐）：同一 FlashVLA 权重、只关异步（`OVERLAP_STEPS=0`），分离"更快解码"与"异步重叠"各自的贡献。
5. **补 Goal 的基线**（可选）：换回 openpi 原始 π0.5 权重复核 Goal 的 95.16 vs 98.0，确认 −2.84 pt 是否来自权重移植。
