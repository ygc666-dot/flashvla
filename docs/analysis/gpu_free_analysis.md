# FlashVLA vs π0.5 —— LIBERO 评测数据整合与单步耗时差异分析

> **数据来源**
> - FlashVLA（`d=1`，异步流式解码）：`results_source_free/ov1/{seed1000…seed5000}/{libero_spatial,libero_object,libero_goal,libero_10}/eval_info.json` + 同级 `.log`
> - π0.5 基线（`d=0`，同步）：`results_pi05_baseline/ov0/{seed1000…seed5000}/{...}`（同结构）
> - 对照参考：`README.md` §Performance / §Latency Benchmark；上一轮 FlashVLA 运行 `results/ov1`（2026-10-30）
> - 规模：每套件每 seed 10 task × 50 episode = 500 episode；5 seed × 4 套件 × 2 模型 = **20 000 episode**
> - 指标定义：`time_per_step = 1000 × 平均 episode 墙钟 / 平均执行步数`（`sim_eval/libero/eval.py:449, :790, :801`），**含 `env.step` + 双视角 360×360 EGL 渲染**，与 README 中 `Time/Step` 的定义一致
> - 聚合方式：先在 seed 内按套件聚合，再对 5 个 seed 取 `mean ± std`；总体为 4 套件等权平均。配对统计把 `(seed, suite, task, episode_idx)` 对齐（同 seed ⇒ 同初始状态）
> - 机器：8×NVIDIA **L40S**（共享节点），2×Intel Xeon Gold 6330（28 核/路，112 线程，2.0 GHz 基频），`MUJOCO_GL=egl`，`OMP_NUM_THREADS=16`，`batch_size=1`，`max_parallel_tasks=1`

## 0. 结论速览

| 项目 | 论文 π0.5 | 本机 π0.5 | 论文 FlashVLA (d=1) | 本机 FlashVLA (d=1) |
| :-- | :--: | :--: | :--: | :--: |
| 平均成功率 (%) | 96.9 | **95.69** | 97.8 | **96.96** |
| ΔSR（FV − 基线） | +0.9 | **+1.27**（p = 6.2e-7） | — | — |
| 平均步数 | 156.0 | 161.11 | 158.0 | 167.89 |
| **单步耗时 (ms)** | 53.8 | **46.73** | 22.1 | **34.95** |
| 单步加速比 | — | — | **2.43×** | **1.337×** |
| episode 墙钟 (s) | 8.4 | 7.17 | 3.5 | 5.64 |
| 总墙钟（10 000 ep） | — | 23.51 h | — | **19.08 h（1.23×）** |

**三句话结论**

1. **成功率侧复现成立**：π0.5 95.69%、FlashVLA 96.96%，相对排序与论文一致（长任务 +3.68 pt 最显著），差值 +1.27 pt 在配对检验下显著（p = 6.2e-7）。绝对值比论文低 0.8–1.3 pt，且两模型同向偏低，属环境/权重来源残差而非方法问题。
2. **单步耗时侧不对称**：π0.5 比论文**快 13%**（46.73 vs 53.8），FlashVLA 比论文**慢 58%**（34.95 vs 22.1）。这个不对称说明差异不在"我们的机器整体更慢"，而在**每步固定开销（地板）与推理成本的结构**。
3. **本机的 1.337× 已接近物理上限**：实测每步非模型地板 ≈ 34.2–34.9 ms；把 FlashVLA 的推理成本压到 0，单步也只能到 34.2 ms，即 **1.365× 封顶**，实测 1.337× = **上限的 98%**。论文 22.1 ms **低于本机的"零推理地板"**，两者不在同一可比区间；进一步按论文自身数据反解，可完全复现其 53.8 → 22.1（见 §4.5）。

### 3.4 地板分解（把单步耗时拆成"模型"与"非模型"两段）

评测实现里每步的动作来源分两类，日志逐 rollout 统计（`sim_eval/libero/eval.py:174-180`，计时只包住 `action_manager.act()`，`env.step` 在 `:191` 之外）：

- `transition` = 触发推理/换 chunk 的那一步（同步模式下即阻塞等推理的全部时间）
- `internal` = 复用缓存 chunk 的普通步（实测 0.010 ms，可忽略）

由此 `Time/Step = 摊销推理/步 + 非模型地板`，其中 `摊销推理/步 = 每 episode 的 transition 总耗时 / 每 episode 步数`。地板是**模型无关**的，所以两个模型在同一套件上算出的地板应相等——这正是下面的交叉验证。

| Suite | 模型 | Time/Step | 每步 transition 次数 | transition 均值 | **摊销推理/步** | **地板** | 推理占比 |
| :-- | :-- | :--: | :--: | :--: | :--: | :--: | :--: |
| Spatial | π0.5 | 58.96 | 1/5.15 步 | 65.7 ms | **12.76** | **46.22** | 21.6% |
| Spatial | FV | 44.03 | 2/5.2 步 | 1.85 ms | **0.71** | **43.32** | 1.6% |
| Object | π0.5 | 43.22 | 1/5.11 步 | 59.5 ms | **11.64** | **31.58** | 26.9% |
| Object | FV | 31.85 | 2/5.2 步 | 1.91 ms | **0.74** | **31.12** | 2.3% |
| Goal | π0.5 | 45.69 | 1/5.13 步 | 58.3 ms | **11.37** | **34.32** | 24.9% |
| Goal | FV | 34.52 | 2/5.2 步 | 1.89 ms | **0.73** | **33.79** | 2.1% |
| Long | π0.5 | 39.06 | 1/5.06 步 | 57.9 ms | **11.44** | **27.61** | 29.3% |
| Long | FV | 29.40 | 2/5.1 步 | 1.80 ms | **0.71** | **28.69** | 2.4% |

**读法与校验**

1. **地板一致性极好**：Object Δ0.5 ms、Goal Δ0.5 ms、Long Δ1.1 ms（相对误差 1.6%–4.0%）。这既验证了分解方法，也证明两轮评测用的是同一套仿真/渲染环境、口径可比。Spatial 仍有 +2.9 ms 的残差（π0.5 侧地板偏高），对应它在 §3.2 里 5.0% 的波动，属残余负载噪声。
2. **异步确实把推理藏住了**：FlashVLA 的可见等待只有 0.71–0.74 ms/步，而它每个 episode 有 47–107 次 transition 事件（约合 24–54 次真实推理，每 5.2 步一次）；`internal = 0.010 ms`。日志里每条 rollout 的 `transition.max` 都稳定在 **25.8–26.0 ms**（每个 episode 第一次推理是阻塞的，无法被隐藏），这正好是 **FlashVLA 在本机的单次推理延迟 ≈ 26 ms**，与 README 的 26.7 ms（RTX 4090，2 视角）几乎相同——即**模型侧没有变慢**。
3. **π0.5 的单次推理 = 57.9–65.7 ms**（每 5.1 步一次），摊销 11.4–12.8 ms/步。README 的 55.4 ms（4090，3 视角，编译后）与之同量级（我们 +5%~19%，且基线多一路空相机、机器不同），说明**本次基线是编译生效的、与论文 latency 表同口径的基线**。
4. **地板占 π0.5 单步的 71%–78%，占 FlashVLA 的 97%+**。也就是说本机是"**仿真密集型**"而非"推理密集型"环境——这就是加速比上不去的根因。

> transition 次数为什么 FlashVLA 是 π0.5 的约 2 倍：异步模式下 `eval.py:174` 把"**发起下一次推理**"（`chunk_index == n_action_steps - overlap`）和"**晋升下一个 chunk**"（`chunk_index == 0`）两步都计为 transition（见 `flashvla/async_manager.py:113-119, :244`）。每 5 个动作仍然只做 **1 次真实推理**，只是被拆成"非阻塞派发"+"同步取用"两次可观测事件。

| Goal | 33.79 | 1.352× | 1.324× | 97.9% |
| Long | 28.69 | 1.361× | 1.328× | 97.6% |
| **平均** | **34.23** | **1.365×** | **1.337×** | **97.9%** |

**结论：FlashVLA 在本机已经跑到地板允许的上限的 98%，继续优化推理没有收益，唯一的杠杆是把地板降下来。**

降低地板能换来什么（按 `(S+11.8)/(S+0.7)` 外推）：

| 假设地板 | 31.1（object 现状） | 26.2（−25%） | 17.4（−50%） | 12.2（−65%） |
| :-- | :--: | :--: | :--: | :--: |
| 预期加速比 | 1.34× | 1.41× | 1.61× | 1.86× |

即：**即便把地板砍半，本机也只能到 1.6×**；论文的 2.43× 对应的是"地板 ≈ 22 ms + 基线推理成本 ≈ 32 ms/步"的另一套测量条件（§4.5）。

| Spatial | 97.28 | 98.8 | −1.52 | 96.32 | 98.8 | −2.48 |
| Object | 98.04 | 98.2 | −0.16 | 99.44 | 99.6 | −0.16 |
| Goal | 95.52 | 98.0 | −2.48 | 96.48 | 97.6 | −1.12 |
| Long | 91.92 | 92.4 | −0.48 | 95.60 | 95.4 | **+0.20** |
| **平均** | **95.69** | **96.9** | **−1.21** | **96.96** | **97.8** | **−0.84** |

- 两模型**同向偏低**（−0.84 / −1.21 pt），说明是共同的环境/权重来源残差，而不是某一方实现有问题；
- ΔSR 方向一致：本机 +1.27 vs 论文 +0.9；
- Long 项最吻合（π0.5 −0.5、FV +0.2），是复现质量最高的一格；
- 需注意基线权重是 lerobot 格式的移植权重（`pepijn223/pi05_libero_31_9_non_q`），**不是** openpi 的 JAX 原始权重，Goal/Spatial 上的偏低有相当一部分应归因于此。

### 4.2 单步耗时（差异的核心）

| 口径 | π0.5 | FlashVLA d=1 | 加速比 |
| :-- | :--: | :--: | :--: |
| 论文 Time/Step（RTX 4090） | 53.8 ms | 22.1 ms | 2.43× |
| **本机 Time/Step（L40S）** | **46.73 ms** | **34.95 ms** | **1.337×** |
| 偏差 | **−13.1%（更快）** | **+58.1%（更慢）** | 0.55× |
| 参考：论文单次推理延迟（4090） | 45.8 ms(2v) / 55.4 ms(3v) | 26.7 ms(2v) / 36.8 ms(3v) | 1.7–2.1× |
| 本机单次推理（实测） | 57.9–65.7 ms | **≈26 ms**（每轮 rollout 首次阻塞推理） | 2.2–2.5× |

**这张表最值得注意的不是"我们慢了"，而是这个不对称**：

- 基线侧我们**比论文更快**（46.73 vs 53.8，−13%）；
- FlashVLA 侧我们**比论文慢 58%**（34.95 vs 22.1）；
- 而模型侧的单次推理延迟两边几乎一样（π0.5 58–66 ms 对应论文 55.4 ms；FV ≈26 ms 对应论文 26.7 ms）。

模型没变慢、基线没变慢 → **差异只能来自"每步固定开销（地板）"和"基线那一步里除了模型推理之外还阻塞了什么"**。

### 4.3 一个硬约束：论文的 22.1 ms 低于本机的零推理地板

本机实测地板：Spatial 43.3、Object 31.1、Goal 33.8、Long 28.7 ms（均值 34.2）。

> **即使把 FlashVLA 的推理成本压到 0，本机单步也到不了 22.1 ms。**

所以 34.95 → 22.1 的这段差距**不可能由"FlashVLA 实现得更快"来解释**。反过来，用论文自己给的两个数字做自洽性检验：

设地板为 S、π0.5 每步摊销推理为 I、FlashVLA 每步可见开销为 i≈0.7 ms：

- 由论文 FV：`S + i = 22.1 → S ≈ 21.4 ms`
- 由论文 π0.5：`S + I = 53.8 → I ≈ 32.4 ms/步`

而 `I = 单次推理 / 5 步`，即 π0.5 在论文那轮里**每调用一次推理约 162 ms**。但论文 §Latency Benchmark 自己给的 π0.5 是 **45.8 / 55.4 ms**（编译 + CUDA Graph）。两者差 **≈3 倍**。

也就是说：**论文的 Time/Step 表里 π0.5 与 FlashVLA 的 31.7 ms/步差额，相当于每次推理省下 158.5 ms，而论文自己的延迟表只允许每次推理省 19.1–28.7 ms（摊到每步 3.8–5.7 ms），相差 5.5 倍。** 这两组数字无法在"同一地板 + 同一推理成本"的模型下同时成立。

### 4.4 归因（按贡献排序）

#### H1（主因）—— 论文基线那一行很可能**没有开 `torch.compile` / CUDA Graph + kernel fusion**

证据链：

1. **脚本默认行为**：`sim_eval/libero/eval.sh:34-46` —— `d>0` 时 `COMPILE_MODEL=true`，`d=0` 时**默认 `false`**，且 `FUSE` 跟随 `COMPILE_MODEL`。也就是说**开箱即用的 π0.5 基线（d=0）是不编译的**，而 FlashVLA（d>0）**必须编译**（否则 launch 阻塞、异步失效）。论文的 Time/Step 主表若按脚本默认跑，天然就是"**未编译基线 vs 编译 FlashVLA**"。
2. **数值对得上**：π0.5 eager 模式（10 步 Euler、无 CUDA Graph、逐 step 回 Python）单次推理落到 120–200 ms 量级是常见值；取 162 ms 则 32.4 ms/步，与论文 53.8 严格吻合（21.4 + 32.4 = 53.8），同时 FV = 21.4 + 0.7 ≈ 22.1 ✔ **两个数字一次性自洽**。
3. **反证**：若论文基线也是编译的（55 ms/次 → 11 ms/步），则地板必须 ≈42.8 ms，FlashVLA 就应 ≈43 ms，而不是 22.1 —— 与论文自相矛盾。
4. **README 的作用域**：README 只在校准小节写"π0.5 与 FlashVLA 使用相同的 CUDA Graph 与 kernel fusion"，那是**延迟基准（`benchmark_latency.py`）**的口径（README:102-104），并未声明 §Performance 的 Time/Step 表也用同一条件。

本次实验是**显式编译了基线**（`COMPILE_MODEL=true FUSE=true`，见 §1.1），因此我们的对比是"编译 vs 编译"，这本身是**更公平、更能反映方法增量**的口径，但它与论文 2.43× 的前提不同——**这是 1.337× vs 2.43× 的最大单一来源**。

#### H2（次因）—— 每步固定开销（地板）本机比论文高约 60%

本机地板 34.2 ms（均值），论文隐含地板 ≈21.4 ms。可能的构成差异：

| 可能项 | 本机情况 | 影响 |
| :-- | :-- | :-- |
| CPU 单核性能 | Xeon Gold 6330 @2.0 GHz（数据中心 U） | MuJoCo 物理步进是单线程，IPC/频率都远低于桌面级 i9/Ryzen |
| 共享节点争抢 | 8×L40S / 112 线程多人共用，本次 1–4 个 job 并发 | 实测与单步耗时 r = +0.38；同配置跨窗口漂移 6–14%（§2.4） |
| 渲染路径 | EGL 离屏 2×360×360 → CPU resize 224 | 日志有 `No OpenGL_accelerate` 警告，部分 GL 加速未启用 |
| 观测预处理 | 实测（2 视角 360→224 + 归一化 + H2D）**仅 ≈0.6 ms** | **不是主要项**，可排除 |
| 串行评测 | `batch_size=1`、`max_parallel_tasks=1` | 无吞吐摊薄，纯延迟受限 |

> 注意：地板的**大头不是预处理，而是 MuJoCo 物理 + EGL 渲染 + 环境/策略预处理器（含 tokenizer）+ Python 调度**。要把这几项拆开，需要在空闲机器上单独做一次 `env.step` 微基准（§6）。

#### H3（次要）—— 论文是 5 次 run 平均，本次是 5 个 seed，且窗口不同

- 论文的 5 run 与我们的 5 seed 不是同一个统计概念（前者可能含不同机器/时段）；
- 本机自身窗口漂移已达 6–14%（§2.4），所以任何 10% 量级的差异都不具备判别力，但 58% 的差异远超噪声，必须用 H1/H2 解释。

### 4.5 一句话重构（数字层面完全闭合）

| 量 | 论文（反解） | 本机（实测） | 倍率 |
| :-- | :--: | :--: | :--: |
| 每步非模型地板 S | **≈21.4 ms** | **≈34.2 ms** | 1.60× |
| π0.5 每步摊销推理 I | **≈32.4 ms**（≈162 ms/次，eager） | **≈11.8 ms**（≈58–66 ms/次，编译） | 2.75× |
| FlashVLA 每步可见开销 i | ≈0.7 ms | ≈0.7 ms | 1.0× |
| 推出 π0.5 Time/Step | 21.4 + 32.4 = **53.8** ✔ | 34.2 + 11.8 = 46.7 ✔ | — |
| 推出 FV Time/Step | 21.4 + 0.7 = **22.1** ✔ | 34.2 + 0.7 = 34.9 ✔ | — |
| 推出加速比 | **2.43×** ✔ | **1.337×** ✔ | 0.55× |

**结论：`2.43× → 1.337×` 的差额可以完全分解为两件事——(a) 论文基线未编译（推理成本 2.75×）与 (b) 本机地板高 1.6×。两者都不是 FlashVLA 实现的问题。** FlashVLA 的模型侧（26 ms/次、可见等待 0.7 ms/步、`internal` 0.01 ms）在本机与论文持平甚至更好。

## 6. 局限与建议的验证实验（按性价比排序）

1. **验证 H1（最关键，1–2 h）**：同机同 seed 跑一轮**不编译的 π0.5 基线**，只跑 1–2 个套件：
   ```bash
   export OUTPUT_ROOT=/home/zjr/StreamingVLA/flashvla/results_pi05_nocompile
   GPUS=0 SUITES="libero_object libero_goal" N_EPISODES=50 \
   COMPILE_MODEL=false FUSE=false \
   POLICY_PATH=/home/zjr/StreamingVLA/flashvla/ckpt/pi05_libero \
   bash sim_eval/libero/eval.sh 0 1000
   ```
   预期：`transition` 均值从 58–66 ms 升到 ~150–200 ms，Time/Step 从 ~44 升到 ~65–70 ms，加速比升到 **~1.9×**。若成立，H1 即被证实，也说明论文 2.43× 与我们的 1.337× 不是同一对比条件。
2. **拆解地板（0.5 h，需空闲卡）**：写一个只跑环境的微基准，分别计时 `env.step`（含渲染）/ 关闭渲染的 `env.step` / `env_preprocessor+preprocessor`，把 34.2 ms 拆成"物理 / 渲染 / 预处理 / 调度"四项。这是把 H2 从定性变定量的唯一办法。
3. **纯推理延迟对标**：`benchmarks/benchmark_latency.py --num_views=2/3`，与 README 的 45.8 / 55.4 / 26.7 ms 直接对齐（注意该基准会下载几十 GB 的 `HuggingFaceVLA/libero`）。
4. **单流 A/B 交替重测**：同一 session、同一空闲卡，`π0.5 → FV → π0.5 → FV`，彻底消除窗口偏差（本次两轮分别跨 11-12→11-14 与 11-13→11-14，且内部有 2–3 路并发）。
5. **降低地板的正向实验**：`OMP_THREADS=4` + `taskset` 绑核 + 独占卡，看地板能否从 34 ms 压到 26 ms 以下；若能，加速比应升至 ~1.41×，可直接支撑地板假说。
6. **Spatial 复核**：Spatial 是唯一出现"FV 更差（−0.96 pt）+ 多走 14.5% 步数 + 地板残差 2.9 ms"的套件，建议在干净窗口重测一次，确认是 d=1 的固有代价还是噪声。
